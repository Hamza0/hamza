I started programming with GW-BASIC at 13. Learning Java in depth later helped me think about how a program's parts work together when something goes wrong.

## Give information a clear meaning

An amount without a currency leaves an assumption unstated. I prefer to make rules like that explicit in the code, where they can be checked.

The same questions guide my work on web applications and business systems: what does this information mean, who may change it and what must remain true?

## Keep responsibilities separate

In a Spring Boot design, I would separate the part receiving web requests, the service applying business rules and the code accessing the database.

I would provide each service's dependencies when it is created. That makes them visible and easier to replace in tests. Moving money between accounts should be one coordinated operation, rather than unrelated updates scattered across request-handling code.

## Thinking about a banking API

This is an independent design exercise with synthetic data, not a production banking system or client implementation.

For a simulated CAD 25.00 transfer, I would use exact decimal amounts. [Oracle's BigDecimal documentation](https://docs.oracle.com/javase/8/docs/api/java/math/BigDecimal.html) explains why starting with a binary floating-point value can introduce an approximation.

This illustrative Java type checks a positive CAD amount; imports are omitted:

```java
record CadTransferAmount(BigDecimal value) {
    CadTransferAmount {
        value = value.setScale(2, RoundingMode.UNNECESSARY);
        if (value.signum() <= 0) {
            throw new IllegalArgumentException("Amount must be positive");
        }
    }
    String currency() { return "CAD"; }
}
```

I would create it with `new BigDecimal("25.00")`. The two decimal places apply to this CAD example, not every currency. The check refuses rounding that would change the requested amount.

An illustrative request, with a placeholder token:

```http
POST /transfers HTTP/1.1
Content-Type: application/json
Authorization: Bearer <token>
Idempotency-Key: transfer-example-001

{"fromAccount":"account-a","toAccount":"account-b","amount":"25.00","currency":"CAD"}
```

I would check different accounts, matching currencies, permission to debit, whether the destination can receive funds and sufficient available funds for this no-overdraft example.

Balances, matching debit and credit records, and the operation record would share one database transaction. Spring's [`@Transactional` rules](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html) require the service call and rollback settings to be configured correctly. A rollback cannot undo a completed action in another service.

To prevent simultaneous requests spending the same balance, I would lock both account rows in consistent order before checking funds. [PostgreSQL's locking guidance](https://www.postgresql.org/docs/current/explicit-locking.html) explains that approach. Every balance-changing path would need to follow it.

I would also store a request key, its caller, submitted details and result. A database uniqueness rule would prevent concurrent duplicates; an unchanged retry would return the saved result. Reusing the key with different details would be rejected. Temporary in-memory storage would not cover restarts or multiple servers.

## Test the failures

Proposed database tests would cover valid transfers, insufficient funds, duplicate attempts and changed request details. Simultaneous withdrawals would check overspending. A failure after the first write would check that balances and debit-and-credit records all roll back.

These are design and test proposals, not claims of a completed banking implementation.
