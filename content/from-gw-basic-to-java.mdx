If you're learning to code, ask what should happen when something fails. That question shaped my path from GW-BASIC to Java and how I think about business software.

## Give information a clear meaning

I started with GW-BASIC at 13. Java came later and was the first language I learned in depth.

It helped me ask better questions. If you hand a program an amount, which currency does it mean? Who may change it? I prefer to make those rules explicit in code rather than leave you guessing.

## Keep responsibilities separate

In a Spring Boot design, I would separate the part receiving web requests, the service applying business rules and the code accessing the database.

I would provide each service's dependencies when it is created, making them visible and easier to replace in tests. If you're moving money, the two balance updates need one place coordinating them.

## Thinking about a banking API

This is an independent design exercise with synthetic data, not a production banking system or client implementation.

Imagine a CAD 25.00 transfer. I would use exact decimal amounts. [Oracle's BigDecimal documentation](https://docs.oracle.com/javase/8/docs/api/java/math/BigDecimal.html) explains why starting with a binary floating-point value can introduce an approximation.

This illustrative Java type checks a positive CAD amount; imports are omitted:

```java
record CadTransferAmount(BigDecimal value) {
    CadTransferAmount {
        value = value.setScale(2, RoundingMode.UNNECESSARY);
        if (value.signum() <= 0) {
            throw new IllegalArgumentException("Amount must be positive");
        }
    }
    String currency() { return "CAD"; }
}
```

I would create it with `new BigDecimal("25.00")`. Two decimal places apply to this CAD example, not every currency. The check refuses rounding that would change your requested amount.

Before transferring, I would check distinct accounts, matching currencies, permission to debit, whether the destination can receive funds and sufficient funds for this no-overdraft example.

Balances, matching debit and credit entries, and the operation record would share one database transaction, saving or cancelling together. Spring's [`@Transactional` rules](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html) require the service call and rollback settings to be configured correctly. Cancelling database work cannot undo a completed action elsewhere.

I would lock both account rows in consistent order before checking funds, following [PostgreSQL's locking guidance](https://www.postgresql.org/docs/current/explicit-locking.html). Every balance-changing path would need that discipline.

For retries, I would store a request key, caller, submitted details and result. A database uniqueness rule would prevent concurrent duplicates. An unchanged retry returns the saved result; changed details are rejected. Temporary memory would not cover restarts or multiple servers.

## Test the failures

I would test valid transfers, insufficient funds, retries, changed details and simultaneous withdrawals. A failure after the first write should cancel the balance changes and matching entries together.

These are proposed database tests, not evidence of a completed implementation.
