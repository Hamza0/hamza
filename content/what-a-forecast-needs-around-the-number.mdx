---
title: "What a Forecast Needs Around the Number"
publishedAt: "2026-07-29"
summary: "Assumptions, source dates and clear comparisons help people use forecasting tools without losing the context behind the results."
---

A forecast can be presented as a single number, but that number rarely tells the whole story. Someone using it needs to understand what it describes, what went into it and which assumptions might change the result.

Working on web experiences for modelling and forecasting has made me pay attention to that surrounding context. The interface has a practical responsibility: help people understand the output without making it appear more certain than it is.

I start with the question the tool is meant to support. Is someone comparing scenarios, exploring a planning period or trying to understand a particular workforce measure? Those are different tasks. A page that puts every available output in front of the user can make all of them harder.

The labels need to do useful work. A time period, unit, geography and source date should be easy to find. If a value represents a projected requirement rather than an observed count, that distinction belongs near the value. It should not depend on someone opening a separate technical document.

Assumptions deserve similar treatment. An input can look like a simple dropdown while representing a significant choice about the scenario being explored. Plain language helps explain what the choice changes and what remains fixed. Sensible defaults are useful, but users should be able to see which defaults they are working with.

Comparisons also need a stable reference. When someone changes an input, the experience should make it clear which result has changed and what they are comparing it against. If the reference period or source has changed as well, a visual difference alone may be misleading.

There is room for detail without putting every explanation on the first screen. A short definition beside a result, an accessible table and a clearly labelled assumptions section can give people different ways into the same information. Downloaded results need context too. A number copied into another document should still carry its period, units and scenario name.

None of this replaces the work behind the model. It makes that work easier to interpret. The interface should also be clear when information is unavailable or a selected combination cannot produce a result, rather than quietly substituting a value.

A useful forecasting experience gives people enough context to ask better questions. The number matters, but so does the explanation that travels with it.
