A useful financial correction keeps the original record and explains the change. Someone reviewing the account should be able to understand how the final amount was reached.

I worked on this approach while building and maintaining a [business operations platform](/projects/production-operations-platform).

## Keep the original and the correction

Suppose a sale recorded as $100 should have been $80. Replacing the first amount would hide part of the story. A reversal and replacement can show it:

| Record | Amount |
| --- | ---: |
| Original sale | $100 |
| Reversal | -$100 |
| Replacement | $80 |
| Final amount | $80 |

This is a simple illustration. Real applications also need rules for linked payments, taxes and reports. The correction should make the history understandable without assuming every financial workflow works the same way.

## Make the changes succeed together

A PostgreSQL [database transaction](https://www.postgresql.org/docs/current/tutorial-transactions.html) groups changes so they can be saved or cancelled together. The correction must include all required writes, with the original, reversal and replacement kept consistent.

If a required write fails, the whole correction should roll back. Leaving half a correction could produce a misleading balance.

Retries need a separate safeguard. The system must recognise a correction that already succeeded. Depending on the design, a [unique constraint](https://www.postgresql.org/docs/current/ddl-constraints.html#DDL-CONSTRAINTS-UNIQUE-CONSTRAINTS), a database rule that rejects duplicate identifiers, can help prevent the same correction from taking effect twice.

## Check who may change the record

The person making a correction must have permission for that business and record. Knowing a record's identifier is not permission to view or change it.

Reports need the same access checks when finding the corrected version. I check permissions, exact amounts, retained history and returned results separately. A speed improvement must preserve all four.

## Test what happens when things go wrong

I want checks for invalid input, missing permissions, interrupted corrections and repeated attempts. Reports must interpret the resulting history correctly too.

The screen needs attention as well. If refreshing fails, it should not present an old balance as a confirmed current result.

The [case study's validation section](/projects/production-operations-platform#testing-and-production-validation) records the checks performed on this platform and the limits of the live-system evidence. Together, those details make the result easier to assess.
