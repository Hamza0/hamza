When you correct a financial amount, you still need to explain the original record. I keep the change traceable so the final balance has a clear history.

I worked on this approach while building and maintaining a [business operations platform](/projects/production-operations-platform).

## Keep the original and the correction

Suppose you recorded a $100 sale that should have been $80. Replacing the amount hides part of the story. A reversal and replacement can show you what changed:

| Record | Amount |
| --- | ---: |
| Original sale | $100 |
| Reversal | -$100 |
| Replacement | $80 |
| Final amount | $80 |

This is a simple illustration. Your application also needs rules for linked payments, taxes and reports. I would check those relationships before choosing how a correction should work.

## Make the changes succeed together

A PostgreSQL [database transaction](https://www.postgresql.org/docs/current/tutorial-transactions.html) groups changes so they can be saved or cancelled together. I want every required correction write inside that boundary.

If one required write fails, the whole correction should roll back. You should not be left with half a correction and a misleading balance.

Retries need another safeguard: recognising a correction that already succeeded. Depending on the design, a [unique constraint](https://www.postgresql.org/docs/current/ddl-constraints.html#DDL-CONSTRAINTS-UNIQUE-CONSTRAINTS), a database rule that rejects duplicate identifiers, can help stop the same correction taking effect twice.

## Check who may change the record

If you can see a record's identifier, that does not automatically give you permission to change it. I check access for the business and the specific record.

Reports need those checks too when they find the corrected version. I treat permissions, exact amounts, retained history and returned results as separate concerns. A speed improvement must preserve all four.

## Test what happens when things go wrong

I want to know what happens with invalid input, missing permissions, an interrupted correction or a repeated attempt. Reports must still interpret the history correctly.

I also check what you see. If refreshing fails, an old balance should not appear to be a confirmed current result.

The [case study's validation section](/projects/production-operations-platform#testing-and-production-validation) records the checks performed on this platform and the limits of the production evidence. You can assess both the result and what remains unconfirmed.
