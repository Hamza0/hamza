A dashboard total can be wrong even when every source record is correct. One common cause is adding an order amount after joining orders to their line items. The join repeats the amount for each matching item, and the total counts it more than once.

Before changing the calculation, establish what the total represents, which records belong in it and whether those records are complete.

## Agree on the meaning of the total

An order total, an invoiced amount and a payment received describe different things. Two reports can disagree because they use different definitions, date ranges or inclusion rules.

Write down the business account, reporting period, currency and relevant statuses. Check whether the source represents current records, a history of changes or a mixture of both. Those choices determine what should contribute to the result.

Keep source differences visible until they are understood. Making two numbers agree is only useful when they are meant to measure the same thing.

## How $180 becomes $280

Consider an illustrative shop with two orders. Order 101 totals $100 and contains two items. Order 102 totals $80 and contains one item. The correct combined order total is $180.

A report joins the orders table to the items table so it can show product details. Its intermediate result looks like this:

| Order | Matching item | Order total |
| --- | --- | ---: |
| 101 | First item | $100 |
| 101 | Second item | $100 |
| 102 | First item | $80 |

Adding the final column produces $280. Nothing was duplicated in the source orders table. The report changed from one row per order to one row per item, while continuing to add an order-level amount.

This follows PostgreSQL's [join rules](https://www.postgresql.org/docs/current/queries-table-expressions.html#QUERIES-JOIN): an inner join produces a result row for each matching pair of rows.

## Why DISTINCT can hide the problem

Changing the calculation to `SUM(DISTINCT order_total)` might appear to fix this example. It adds $100 and $80 once each.

However, PostgreSQL's [DISTINCT aggregate behaviour](https://www.postgresql.org/docs/current/sql-expressions.html#SYNTAX-AGGREGATES) removes repeated values of the expression. It does not identify separate orders. If two legitimate orders both total $100, that calculation returns $100 instead of $200.

For an order-total metric, the amount should contribute once per included order. That can mean calculating directly from the filtered orders table, or preparing related data so each order has at most one matching summary row before combining it.

A product-sales metric may instead need item amounts, with its own treatment of quantities, discounts, tax and refunds. It should not silently replace an agreed order-total calculation.

## Check missing values and source freshness

A blank value might mean information was not collected, was not applicable or could not be matched. Treating all three as zero can conceal the distinction. The report needs an explicit rule for missing information and a way to explain material gaps.

Check categories, units and date formats before combining sources. Confirm when the data was last updated and whether the expected records arrived. An import can finish without an error while providing an empty or incomplete input.

The interface should make an incomplete update distinguishable from a complete result.

## Validate with a small, explainable sample

I would start with records that someone can check by hand:

1. Record the metric definition and select a small reporting period.
2. Calculate the expected result from the source records before adding joins.
3. Inspect intermediate rows for repeated IDs and compare counts before and after each transformation.
4. Include several items, separate orders with equal totals and missing related records where they are relevant.
5. Compare the corrected result with the dashboard under the same filters, then capture the example in a regression test.

An inflated total can influence purchasing, staffing or sales decisions. Keep the reconciled sample with the query so future changes can be checked against the same expected result.
