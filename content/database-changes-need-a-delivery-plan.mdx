A migration can run successfully while leaving the application wrong. A function signature may still match even though its permissions, row ordering or interpretation of a corrected transaction has changed. My delivery plan starts with those observable behaviours.

## Define what must stay true

The [Production Operations Platform](/projects/production-operations-platform#technical-solution) includes financial corrections that retain the original transaction, record its reversal and link a replacement. The correction is atomic: if part of it fails, the operation rolls back as one unit.

That design preserves an audit trail, but it gives readers more work to do. A list must resolve the current records without treating an original and its replacement as two unrelated current transactions. Optimizing that read path must preserve the writer contract, historical data and tenant boundaries.

For this change, I treated response parity and exact financial results as release requirements. The validation also covered correction and retry behaviour, permission boundaries and cross-tenant denial. Checking only a successful request from one permitted account would leave important failure paths untested.

## Separate compatibility from deployment order

Before a database release, I identify which application calls, reports and integrations depend on the definition being changed. If a field or function contract must change, an additive transition can let old and new application versions coexist. Removing the old contract belongs after its consumers have moved.

This is a planning rule, not a claim that every migration needs a large compatibility framework. For a focused read optimization, preserving the existing interface can be the smaller and more reviewable choice. Changes to permissions or financial writers should not slip into an unrelated performance patch.

## Make recovery concrete

Rolling back application code does not undo transformed data. I distinguish reversible definition changes from writes that require a recovery procedure. For data migrations, I want preflight checks, a dry run where practical, explicit write scope and validation of the resulting records. A rollback plan should say what it restores and what evidence confirms that restoration.

## Check the deployed state, then the user path

For the platform release, production database checks verified the intended change while preserving migration history, permissions and related definitions. Local tests and browser regressions supplied separate evidence about behaviour.

Authenticated production list acceptance was unavailable for that release. That limit matters: inspecting a deployed definition is not equivalent to exercising the request as a real authorized user. The [case study’s validation section](/projects/production-operations-platform#testing-and-production-validation) records that distinction alongside the controlled local performance result.

A useful release record names the change, the invariants checked and the checks still outstanding. It gives the next developer a better starting point than “migration succeeded.”
