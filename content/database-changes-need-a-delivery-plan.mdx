A database update can finish successfully while leaving the application wrong. I plan around the information people should see, who may access it and how recovery works.

## Decide what must stay the same

In the [operations and financial platform](/projects/production-operations-platform#technical-solution), a correction keeps the original transaction, records its reversal and links a replacement. If part fails, the correction rolls back as one unit.

Reports must then identify the current version without counting an original and its replacement as two current transactions. Making those reports faster must preserve the history and each business's access restrictions.

For this change, I checked that returned data and financial amounts stayed correct. Checks also covered corrections, retries and attempts to access another business's records. A successful request from one permitted account would not cover those cases.

## Keep existing application calls working

Before a release, I identify the screens, reports and integrations that depend on the database change. A changed field or function may need a transition period while older application versions still use it.

Sometimes adding the new version first lets both coexist. The old version can be removed once its users have moved. For a focused performance improvement, keeping the existing interface may be simpler.

I keep unrelated changes to permissions or financial records out of that update. A smaller change is easier to explain and assess.

## Describe how recovery would work

Restoring older application code does not restore data that has already changed.

I separate changes to database definitions from changes to stored records. For the latter, I want checks before the update, a practice run where practical, a clear limit on what may change and a way to verify the result.

A recovery plan should explain what it restores and how someone will confirm that restoration.

## Check the live system separately

For this release, production database checks confirmed the intended change and preserved migration history, permissions and related definitions. Local tests and browser checks supplied separate evidence about behaviour.

A signed-in test of the list on the live system was unavailable for that release. Inspecting a database definition does not replace that check. The [case study](/projects/production-operations-platform#testing-and-production-validation) records this limit alongside its controlled local performance result.

The release record should tell the next person what changed, what was checked and what still needs confirmation.
