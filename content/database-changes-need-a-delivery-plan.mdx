Your database update finishes, but a report now shows the wrong amount. I plan around the application's behaviour, because a successful update alone cannot confirm that.

## Decide what must stay the same

I start with what you depend on: correct information, appropriate access and records you can trace.

In the [operations and financial platform](/projects/production-operations-platform#technical-solution), a correction keeps the original transaction, records its reversal and links a replacement. If part fails, the correction rolls back together.

Reports then need to find the current version without counting the original and replacement as separate current transactions. Making them faster must preserve that history and each business's access restrictions.

For this change, I checked returned data, exact financial amounts, corrections, retries and attempts to access another business's records. Testing one successful request would have missed important cases.

## Keep existing application calls working

Before a release, I identify the screens, reports and integrations using the database definition I'm changing. Your older application version may still need it during the update.

Sometimes I would introduce the new version first, allowing both to coexist until the old one is no longer used. For a focused speed improvement, keeping the existing interface can be simpler.

I keep unrelated permission or financial-record changes out of that update. You should be able to understand why each change belongs in the release.

## Describe how recovery would work

Restoring older application code does not restore data that has already changed.

I separate changes to database definitions from changes to stored records. For the latter, I want checks beforehand, a practice run where practical, clear limits on what may change and a way to verify the result.

If we need to recover, the plan should tell you what will be restored and how we will confirm it.

## Check the actual user journey

For this release, production database checks confirmed the intended change and preserved migration history, permissions and related definitions. Local tests and browser checks supplied separate evidence about behaviour.

A signed-in test of the list in production was unavailable for that release. Inspecting the database definition does not replace that check. The [case study](/projects/production-operations-platform#testing-and-production-validation) records this limit alongside the controlled local performance result.

I want the release record to leave you with three clear answers: what changed, what was checked and what still needs confirmation.
