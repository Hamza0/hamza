---
title: "Database Changes Need a Delivery Plan"
publishedAt: "2026-10-09"
summary: "A schema change reaches beyond the database. Applications, integrations and reports need a clear path through the transition."
---

Adding a field to a database can look like a small change. The query is straightforward, the application needs the new value and the development environment behaves as expected. The harder questions often appear when the change reaches a live system.

An application, a form integration and a report may all depend on the same record. They do not necessarily update at the same time. A database change therefore needs a delivery plan as well as a technically valid migration.

I first look at the consumers of the data. Which parts of the application read this field? Which processes write it? Does an external system expect the current format? Are there exports or dashboards using a name that now needs to change? These questions help establish the boundaries before implementation begins.

Existing records need particular attention. A required field for new submissions may not exist in older data. That does not automatically mean those records are invalid. The change needs an explicit decision about how to handle missing values, whether a backfill is appropriate and what the interface should show while the transition is incomplete.

Where possible, I prefer a change that allows the old and new application versions to coexist briefly. Adding a new field before relying on it can be easier to manage than renaming or removing a field in one step. The right approach depends on the system, but compatibility should be a deliberate choice.

Verification should include representative existing data. An empty local database can hide issues with unusual values, older records or relationships that are present in production. Checking those conditions in an appropriate test environment is more useful than confirming that a newly created record works.

The release order matters too. If application code reaches production before its expected schema, an ordinary request can fail. If an integration continues sending the old format, a successful application deployment may still leave a broken workflow behind it.

I also want to know what recovery would involve. Reverting application code does not necessarily reverse a data change, especially if records have already been transformed or removed. That is a reason to plan backups, validation and recovery steps before the release.

A good database change leaves the system understandable after deployment. The schema, application behaviour and documentation should agree on what the data means. Getting the migration to run is one part of that work; getting every dependent piece safely through the transition is the rest.
