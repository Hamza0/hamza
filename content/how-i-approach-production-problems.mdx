When someone says a list is slow, I first follow one request. The delay could be in the browser, permission checks or database work.

A page loading successfully does not prove that its forms, reports or connections are working. I start with the feature the person needs to use.

## Find where the time goes

In the [operations and financial platform](/projects/production-operations-platform#root-cause-investigation), a financial list repeated permission checks and looked through history to find corrected records. That work grew even though the response contained only one page of results.

I compared the returned data and measured database execution using synthetic local data. Returning fewer rows would not remove work happening before the page was selected.

The question was which checks could happen once while preserving each business's access restrictions. Useful logs should help trace that request without adding unrelated detail or unnecessary sensitive information.

## Keep the change focused

I changed the read path to make equivalent permission decisions once, identify current records, then filter and select the page before calculating its balances. The code writing financial records and the existing history stayed intact.

Changing that order carelessly could omit records or change totals. A faster response is not useful if it exposes another business's data or returns the wrong amount.

A focused change also makes review and recovery easier. Restoring older code and recovering changed data are different tasks, so the release plan needs to distinguish them.

## Check correctness before speed

Checks covered unchanged results, accurate financial amounts, permissions and denied access to another business's records. Browser checks covered moving between pages, refreshing and recovering from errors.

The controlled local benchmark used the same synthetic data for both versions: **600 historical sales, 120 customers and a 50-row response**. Three HTTP requests per version gave median times of **4,521 ms and 94 ms**, approximately **98% lower**. Each measurement covered the complete request for that page, not every historical record.

These figures describe those local test conditions. They are not measurements of real customer traffic or a promise about live response times.

## Check the customer journey separately

A build or database update succeeding does not prove that a signed-in user can complete the task. A signed-in test of this feature in production was unavailable for that release.

The screen must also explain delayed responses, old values and rejected actions clearly. Repeated button presses should not be the only apparent way forward.

I record the cause, change, checks and remaining uncertainty. The same approach guides my [database release planning](/blog/database-changes-need-a-delivery-plan), giving the next person enough information to assess the work.
