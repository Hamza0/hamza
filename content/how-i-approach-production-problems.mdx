If a page feels slow, I start with the task you're trying to finish. Following one request tells me more than changing code based on a guess.

## Find where your time is going

A page loading does not prove that its forms or reports work. I follow the feature you actually need.

In the [operations and financial platform](/projects/production-operations-platform#root-cause-investigation), a financial list repeated permission checks and searched history for corrected records. That work grew even though the response contained one page of results.

I compared returned data and measured database execution using synthetic local data. Returning fewer rows would not remove work happening before the page was selected.

I looked for checks that could happen once while preserving each business's access restrictions. Useful logs help trace that path without burying it in unrelated detail.

## Keep the change focused

I changed the read path to make equivalent permission decisions once, identify current records, then filter and select the page before calculating its balances. The code writing financial records and the existing history stayed intact.

You still need the right records and amounts. Changing the order carelessly could omit a record, alter a total or expose another business's data.

I also consider recovery. Restoring older code and recovering changed data are different jobs. Keeping the update focused makes that distinction easier to assess.

## Check the answer before the speed

Checks covered unchanged results, accurate financial amounts, permissions and denied access to another business's records. Browser checks covered moving between pages, refreshing and recovering from errors.

The controlled local benchmark used the same synthetic data for both versions: **600 historical sales, 120 customers and a 50-row response**. Three HTTP requests per version gave median times of **4,521 ms and 94 ms**, approximately **98% lower**. Each measurement covered the complete request for that page, not every historical record.

Those figures describe the local test conditions. They are not measurements of real customer traffic or a promise about response times in production.

## Check what you can actually do

A successful build or database update does not prove that you can complete the task after signing in. A signed-in test of this feature in production was unavailable for that release.

The screen matters too. If a response is delayed or a value is old, you need a useful explanation and next step. Repeatedly pressing the button should not be your only apparent option.

I record the cause, change, checks and remaining uncertainty. That also guides my [database release planning](/blog/database-changes-need-a-delivery-plan), so you can see what the evidence supports.
