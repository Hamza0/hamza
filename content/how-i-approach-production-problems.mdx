“The list is slow” describes a symptom. It does not tell me whether the time is spent in the browser, the API, authorization checks or the database. Before changing code, I define the request, the expected response and the conditions that reproduce the delay.

## Follow the work behind one request

In the anonymized [Production Operations Platform case study](/projects/production-operations-platform#root-cause-investigation), a financial list repeated permission checks and resolved historical records to their current corrected versions. That work grew with the history being examined, even though the response contained only one page of results.

I compared before-and-after API responses and profiled database execution using synthetic local data. Returning fewer rows would not remove the repeated work happening before pagination. The useful question was which decisions could be evaluated once while keeping tenant and record-level restrictions intact.

## Keep the change narrow

The read path was changed to evaluate equivalent authorization decisions once, resolve the current candidate records, then filter and paginate before bounded balance aggregation. Financial writers and historical records were left intact.

This order matters. Moving pagination earlier can change which records qualify or how totals are calculated. A faster response is a regression if it drops an eligible record, exposes another tenant’s data or changes a financial result.

## Verify correctness before interpreting speed

Validation covered response parity, financial correctness, permission boundaries and cross-tenant denial. Browser checks covered pagination, refresh and error recovery. I also kept deployment verification separate from performance evidence: a successful build or migration does not demonstrate acceptable behaviour for an authenticated user.

The controlled local benchmark used the same synthetic fixture for both versions: 600 historical sales, 120 customers and a 50-row response. Three HTTP samples per version gave median full-list API times of **4,521 ms and 94 ms**, approximately **98% lower**. “Full-list” means the complete API request for that page, not every historical record.

These measurements demonstrate the effect under those test conditions. They are not live production latency measurements or an uptime promise. Authenticated production list acceptance was unavailable for that release, which remains a separate validation limit.

The investigation is complete when I can explain the cause, the change, the correctness checks and the remaining uncertainty. I use the same discipline when planning [database delivery and recovery](/blog/database-changes-need-a-delivery-plan): make the boundary explicit before calling the release successful.
