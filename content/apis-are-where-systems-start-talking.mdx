You press Submit, wait, then see a timeout. Before you try again, check whether the first request finished. A missing reply does not prove failure.

## Find out what happened

An API lets programs exchange information. When one program stops waiting for a reply, you can get a timeout even though the other program completed its work.

Imagine your website asking a service to create an order:

| What happened | What your website knows |
| --- | --- |
| The request never arrived | No order exists, if this can be confirmed |
| The service is still working | The outcome is unknown |
| The order exists but the reply was lost | You may still see an error |

Stripe's [explanation of safe retries](https://stripe.com/blog/idempotency) covers this uncertainty. I want to establish what happened to the first request before creating another.

## Keep the same request identity

An *idempotent* operation has the same intended effect when repeated as when performed once. The [HTTP specification](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2) explains why that matters. The receiving service must support it; adding an identifier alone cannot prevent duplicates.

On this site's contact form, your submission gets an identifier. If the result is uncertain, the browser keeps that identifier and your original details. The server tells the email provider that an unchanged retry belongs to the same submission.

You still need a fresh spam-check token for each retry. That allows the new attempt to proceed; it is separate from your message's identity.

The provider remembers duplicate requests for a limited time. The server rejects old identifiers before that window expires, and the form prevents edits to an uncertain submission. Retry timing also needs to follow the provider's [error-handling guidance](https://docs.stripe.com/error-low-level).

## Check the request before sending

Before contacting the email provider, the server checks the request's source, size and fields, then verifies the spam token.

Your email address is used for replies. The receiving address stays in server configuration, so the public form cannot send to arbitrary recipients.

## Tell you what is confirmed

The form reports acceptance only when the provider returns a message identifier. That confirms provider acceptance, not arrival in my inbox. Invalid input, pending requests, rate limits and service failures need different handling.

If the outcome is uncertain, your details stay available with a retry explanation.

Automated tests cover invalid requests, escaped email content, retries, simultaneous attempts and a simulated lost reply after acceptance. That last check verifies that retrying does not send twice through the simulated provider. These checks do not prove inbox delivery.
