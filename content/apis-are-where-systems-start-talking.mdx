An API lets programs exchange information. A timeout means the reply did not arrive in time, even if the requested work finished.

## Find out what happened

Imagine a website asking another service to create an order:

| What happened | What the website knows |
| --- | --- |
| The request never arrived | No order exists, if this can be confirmed |
| The service is still working | The outcome is unknown |
| The order was created but the reply was lost | The website may still show an error |

Stripe's [explanation of safe retries](https://stripe.com/blog/idempotency) describes this uncertainty. Waiting longer next time does not establish what happened to the first request.

## Keep the same request identity

An *idempotent* operation has the same intended effect when repeated as when performed once. The [HTTP specification](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2) explains why automatic retries need that safeguard. The receiving service must support it; adding an identifier alone is not enough.

This site's contact form gives each submission an identifier. If the result is uncertain, the browser keeps that identifier and the original details. The server uses it to tell the email provider that an unchanged retry belongs to the same submission.

Retries still need a fresh spam-check token. That proves the new attempt may proceed; it is separate from the message's identity.

The provider remembers duplicate requests for a limited time. The server rejects old identifiers before that window expires, and the form prevents changes to an uncertain submission. Retry timing also needs to follow the provider's [error-handling guidance](https://docs.stripe.com/error-low-level).

## Check the request before sending

The server checks where requests came from, their size and their fields, then verifies the spam token. These checks happen before calling the email provider.

The visitor's email address is used for replies. The receiving address stays in server configuration, so the public form cannot be used to send messages to arbitrary recipients.

## Confirm the result and test failures

The form reports acceptance only after the provider returns a message identifier. That confirms acceptance by the provider, not arrival in the recipient's inbox. Pending requests, invalid input, rate limits and service failures receive different handling.

When the result is uncertain, entered details remain available with a retry explanation. The interface does not assume that nothing was sent.

Automated tests cover invalid requests, escaped email content, unchanged retries, simultaneous attempts and a simulated lost reply after acceptance. The last test checks that retrying does not send twice through the simulated provider. These are application checks, not proof of inbox delivery.
